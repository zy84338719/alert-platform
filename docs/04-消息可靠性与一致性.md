# 04 · Kafka、事务、Outbox 与故障语义

## 1. Topic 与 Key

| Topic | Key | 生产者 | 消费者 | 特征 |
| --- | --- | --- | --- | --- |
| `alert.raw.v1` | `tenant_id/fingerprint` | API | Processor | 主可靠流、同告警顺序 |
| `alert.lifecycle.v1` | `tenant_id/instance_id` | Domain Outbox Relay | History / Correlation | 事务后事件 |
| `alert.incident.v1` | `tenant_id/incident_id` | Domain Outbox Relay | History / Integrations | Incident 变更 |
| `alert.dlq.v1` | 原消息键 | Processor | 修复/重放工具 | 毒消息 |

写端应使用 `acks=all`、合理的 ISR 和生产端幂等；这减少传输层重复但**不替代数据库幂等**。

## 2. Processor 事务步骤

```text
Poll Kafka
  -> Decode + Validate IDL
  -> Begin PG Tx
  -> Lock/optimistically update AlertInstance by fingerprint + episode
  -> Insert event receipt/idempotency record
  -> Insert transition (only if state actually changed)
  -> Upsert Incident (if configured)
  -> Insert Notification Outbox & Domain Outbox (same Tx)
  -> COMMIT
  -> Commit Kafka Offset
```

若 DB Commit 成功、Kafka Offset Commit 失败，重放会重新执行处理流程，但唯一约束和 version check 要阻止重复状态变更/通知。

## 3. Edge ACK 与断网缓冲

- Edge 返回 202 前必须确认本地队列稳定持久化，不能先 ACK 再写缓冲。
- Edge 上传时保持 `transport_id` 和批次中逐事件身份稳定；中心入 Kafka 确认后才能标记该条已传输。
- 假设 2 KiB/event，100 EPS 时每日原始有效载荷约 17.7 GB（16.5 GiB，与 docs/05 §5 同一口径）；Edge 缓冲容量按本地实际峰值与可承受中断时间测算。
- WAL/SQLite 单磁盘非高可用；单机磁盘不可恢复故障会丢失数据，若业务要求区域级零丢失，需要副本存储。
- SSE 断连期间未收到的 HUATUO 数据**无法通过 Edge 缓冲补齐**；应报警并记录缺口。

## 4. Transactional Outbox

- 业务事务写 `notification_outbox` 与 `domain_outbox`。
- Notifier 用 `FOR UPDATE SKIP LOCKED` 领取、持有 lease、失败后退避重试。
- Relay 将 `domain_outbox` 中已提交记录可靠发布到 Kafka，再标记已发送；Relay 重试可能重复发布，消费方保持幂等。
- Relay 使用 `component_leases` 的 `outbox.relay` 租约保证同一时刻只有一个发布者；claim 按 `created_at` 排序，且**同一 key（tenant|aggregate）存在更早的 pending/publishing 行时不会领取新行**，失败发布不会被同聚合的新事件超车。
- 发布尝试达到 `OUTBOX_MAX_ATTEMPTS`（默认 20）后进入终态 `failed`（死信，不再重试，可人工重放），指标 `alert_platform_outbox_dead_letter_total` / `alert_platform_outbox_failed` 暴露积压。
- kafka-go 的 Writer **不是幂等 producer**（无 `enable.idempotence` 等价物）：broker 超时后的重试可能重复消息，投递语义为 at-least-once，不能宣称 exactly-once。
- 无法可靠实现大多数第三方通知的 Exactly Once；支持“至少一次 + 幂等键 + 记录尝试”。

## 5. 通知语义

- 匹配顺序：有效事件 -> Incident -> route policy -> silence/inhibition -> aggregation delay -> outbox。
- 发送前再次校验静默/策略有效期，但要记录使用的 `policy_version`，避免策略变更不可追溯。
- 通知重复键：`subject_type + subject_id + notification_type + channel + receiver + escalation_stage + occurrence_version`。**subject 先绑定 `alert_instance`（W7 起，Incident 尚未落地），Incident 1:1 实体上线后绑定 `incident`**；两类主体键空间隔离，切换期不互相抵消。`notification_outbox.subject_type/subject_id` 与 CHECK 约束落地该规则。
- 第三方 API 429 使用 Retry-After；5xx/超时指数退避；4xx 永久失败应识别具体语义。
- **通知权切换（REL-001/REL-002）**：`ALERT_NOTIFY_MODE=shadow|active|off` 持久化在
  `notification_authority`（mode/generation/effective_at）。任务入队时记录 `created_mode`
  （迁移 0013）：**active 期创建的任务**在被 shadow 打断后，切回 active 仍会补投且仅一次；
  **shadow 期创建的任务是观察记录，切回 active 永不补投**（避免与上游重复的风暴，
  P0-07 守卫）。pre-ledger（created_mode 为空）任务永不领取。
- 接入认证使用 30s 正向凭证缓存（`sourcereg.CachedStore`），管理写（禁用/吊销/创建）立即失效：
  PostgreSQL 故障窗口内 ingest 仍可接收入队，不被认证查询拖死。缓存是**每进程**的——多 API 副本
  部署时，A 副本上的吊销/禁用最多滞后一个 TTL（30s）才在 B 副本生效；安全要求即时吊销时应
  重启/滚动副本或接受该窗口（写入 docs/08 安全评审）。

## 6. 失败模式验收

- Kafka 不可用：直接 API 返回可重试错误；Edge 持久化已确认的本地消息继续排队。
- PG 不可用：不提交消费 Offset；恢复后重放不重复发送通知。
- Worker 重启：不重复 transition/outbox。
- 部分批次失败：V1 定义**整批原子接收**；`PushBatchResponse` 已移除 `accepted_count`（字段 2 reserved），整批成功即 202 + `durable_batch_id`，逐条确认若引入必须是新接口而非复用该响应。
- Channel 返回成功但客户端未收到响应：可发生重复通知，需通过外部幂等支持/平台重复检测降低概率。
