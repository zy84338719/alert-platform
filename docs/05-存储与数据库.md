# 05 · PostgreSQL、ClickHouse 和数据保留

## 1. PostgreSQL 是业务状态事实源

权威业务对象：来源注册、策略快照、当前告警、状态变更、Incident、通知任务、投递尝试、审计。

DDL 初稿见 `migrations/0001_initial.up.sql`（golang-migrate 命名契约 `NNNN_name.up.sql`），包括唯一约束、索引及 Outbox。**运行 Migration 前必须由 DBA 审核**，尤其检查流量下的主键/分区、删除、保留周期和 PITR。本节权威对象清单由集成测试逐表断言（`internal/infrastructure/postgres` 的 `wantTables`，BASE-005）——增删表必须同步改本节与该清单，否则测试红。

`notification_authority`（0009，P8-P0-01）是通知所有权的持久化事实源：`mode`（active/shadow/off）、`generation`（每次模式切换 +1 的所有权纪元）、`effective_at`、`initialized`。`notification_outbox.authority_generation` 记录任务入队纪元，领取只认当前纪元——Shadow→Active 切换（K8s 改 env 重启 Pod）绝不补发历史通知；迁移前（generation 0）的任务不再被领取。

`edge_uplink_credentials`（0010，P8-P0-02）是 Edge 上行身份：`edge_id + tenant_id + allowed_source_ids + token_hash(SHA-256)`，一个凭证可为多个来源上传（受 allowed 集约束，禁用来源即时移出），与 per-vendor Webhook 凭证分离。

## 2. 原始事件存储策略

P0：保留原始 Payload 的引用或裁剪后的短期记录；如原始单条超限，拒绝或存储对象引用。
P2：历史事件进入 ClickHouse（按 tenant/time 分区或 ORDER BY 策略设计），PG 只保留活跃状态和有限短期历史。

不得在 PostgreSQL `alert_instances` 中无限堆积所有重复接收的原始事件。

### ClickHouse 归档（P9-CH-01，代码面就绪；实跑待 INC-007）

- **DDL**：`deploy/clickhouse/0001_transitions.sql`（`MergeTree`，`PARTITION BY toYYYYMM(transition_at)`，
  `ORDER BY (tenant_id, transition_at, transition_id)`，TTL 365 天；TTL 表达式用
  `toDateTime(transition_at)`——ClickHouse 不接受 `DateTime64` 直接作 TTL）。
- **升级注意（R25）**：R25 之前若写入过 1970 时间戳（缺失 protobuf 时间的旧 bug），
  先执行 `scripts/repair_epoch_timestamps.sql`（先输出检测计数，再事务内用 created_at/received_at 修复；
  1970 分区在 CH 会被 TTL 立即删除，修复后重新归档即可）。
- **验收**：`scripts/drill_ch_archive.sh` 在真实 ClickHouse 24.8 容器上跑通
  ingest→PG→archiver→CH→history API（2026-11-17，证据 `docs/evidence/P9-ch-archive-drill-2026-11-17.md`）。
- **写入**：worker 归档任务（`ALERT_CLICKHOUSE_URL` 配置后启用，非关键任务）：每 10s 取一批
  （≤500 行/批、≤10 批/tick）`transition_archive_queue` 中待归档的行（**每个 transition 在写入
  它的同一 PG 事务里入队**，迟到/乱序/边缘重放事件不会漏归档），经 ClickHouse HTTP
  `INSERT ... JSONEachRow` 成功后标记 `done`。`component_leases` 保证单写者；
  ReplacingMergeTree(FINAL) + 唯一 transition_id 保证重复写安全。
  **归档不在任何 PG 写事务内**：CH 故障只暂停归档，不阻塞告警写入；积压由
  `alert_platform_archive_lag_seconds` / `_queue_pending` / `_errors_total` 观测。
- **读取**：`GET /history/v1/transitions?from=&to=&limit=`（Bearer + `alerts:read`）。窗口在 PG 保留期内
  查 PG，超出则查 CH，响应 `archived` 标记数据来源（PG/CH 路由见 `internal/application/history`）。
- **配置**：`ALERT_CLICKHOUSE_URL` / `ALERT_CLICKHOUSE_DB`（默认 `default`）/ `_USER` / `_PASSWORD`；
  `ALERT_HISTORY_PG_WINDOW`（默认 168h）决定 PG/CH 路由边界；未配置 CH 时归档关闭、历史查询仅覆盖 PG 窗口。

## 3. 推荐查询路径

- 当前告警：PG 索引 `(tenant_id,state,severity,updated_at)`。
- 某告警时间线：PG `alert_transitions` / 归档 CH。
- 30 天事件趋势：ClickHouse 离线聚合，不在业务写事务内同步查询 CH。
- 关联检索：先由规范化 resource UID / service ID 查找候选集，不对全表做模糊 JSON 查询。

## 4. 数据生命周期矩阵与对账清理（P10-004）

| 数据类型 | PG | ClickHouse | 清理条件 | 现状 |
| --- | --- | --- | --- | --- |
| 活跃 AlertInstance | 权威存储 | 不需要 | 不清理 | 已落地 |
| 已结束 AlertInstance | 近期保留 | 可选归档 | 到期且引用安全（Incident/审计） | **不自动清理**（需引用检查，保守） |
| AlertTransition | 热窗口保留（`HISTORY_PG_WINDOW`，默认 168h） | `alert_transitions` 归档 | **逐日对账通过且超过 `TRANSITION_RETENTION`（默认 720h）** | 已落地（lifecycle reconciler） |
| 原始 AlertEvent（`event_history`） | 短期保留 | 原始事件归档**尚未实现** | 已确认归档 | **不自动清理**（无归档依据，只能查询/人工治理） |
| Notification Attempt | 近期保留 | 可选 | 审计保留策略 | receipts/notifications/audit 按 RETN 清理 |
| Incident | 权威存储 | 分析副本可选 | 合规策略 | 不自动清理 |
| Audit Log | 权威审计窗口 | 长期归档可选 | 合规保留策略 | RETN-002（30d 派生窗口） |

### Only-after-verified 清理（实现）

`internal/application/lifecycle` 在 `maintenance` profile 中每 `ALERT_LIFECYCLE_INTERVAL`（默认 24h）执行：

1. PG 按 UTC 日聚合 `transition_at < now()-TRANSITION_RETENTION` 的行，返回 `(total, queue_done)`；
2. ClickHouse 按同一 UTC 日统计 `uniqExact(transition_id)`（`FINAL` 去重）；
3. 仅当 **`queue_done == total` 且 `ch_unique >= total`** 时删除该日 PG `alert_transitions`
   （同一事务内先删该日 `done` 队列行）；
4. 任一条件不满足（队列 pending/inflight、CH 计数不足、CH 不可用、未配置 CH）→ **保留整日数据**，
   在报告与 `alert_platform_lifecycle_days_unverified` 中可见。

"CH 写成功一次"绝不触发删除；删除依据是**整日对账**。`ALERT_TRANSITION_RETENTION` 必须 ≥
`ALERT_HISTORY_PG_WINDOW`，否则会删掉热查询仍依赖的 PG 数据。

指标：`alert_platform_lifecycle_transitions_deleted_total`、`_days_verified_total`、`_days_unverified`。

## 5. 数据增长基线

100 EPS * 86400s * 2KiB = 约 16.5 GiB/天（17.7GB/天十进制）。Kafka 3 副本、索引、日志及 PG 页膨胀会增加总占用。实际每条大小和压缩比由 v0.1 采样后再确认。
