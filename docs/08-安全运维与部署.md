# 08 · 安全、Kubernetes、高可用与可观测

## 1. 安全边界

- 外部 DeepFlow Webhook：独立来源 Token 或签名，凭证关联服务器端 Source Registry，不信任来报的 tenant_id。
- Edge -> Center：mTLS 或短期 Token + TLS；设置源配额、请求大小、超时及请求频率。
- 管理 API：JWT/OIDC、RBAC、租户强制注入、对象级授权、操作审计。
- Outbound Webhook：防 SSRF（DNS 和 IP 段检查、重定向限制、代理策略、私网地址访问控制），密钥加密存储，日志脱敏。
- 所有原始 Payload 按数据敏感级别分类，避免把凭证/个人信息直接写入日志或 ClickHouse。
- 生产安全：容器非 root、只读根文件系统（Edge WAL 目录需专用可写 PVC）、NetworkPolicy、最小 RBAC、Secret Rotation。

**NetworkPolicy 出口模型（P8-P1-02）**：Chart 默认按组件拆三条策略（api/worker/edge）。
worker 默认显式放行**公网**通知出口（TCP 80/443，排除 10/8、172.16/12、192.168/16、
169.254/16、100.64/10 与 IPv6 私网/链路本地）——标准 Kubernetes NetworkPolicy
不支持域名白名单，若不放开该规则，默认安装会出现"平台认为已发送、机器人实际收不到"。
需要完全 deny-by-default 时设 `networkPolicy.egress.notificationEgress.enabled=false`
并在 `workerExtraEgress` 中逐条列出渠道地址（有 Cilium 时优先用 FQDN Policy）。
多集群部署且中央 API 位于其他 namespace 时设 `networkPolicy.egress.edgeCentralNamespace`
（端口 `edgeCentralPort`，默认 8080）；默认只允许同 namespace 的 api Pod。

## 2. K8s 建议部署

| 组件 | 运行形式 | 生产起步 | 备注 |
| --- | --- | --- | --- |
| alert-api | Deployment | 2 replicas | HPA / PDB / Anti-affinity |
| alert-worker processor | Deployment | 2 replicas | Kafka Consumer Group |
| alert-worker notifier | 独立 profile Deployment | 2 replicas | DB SKIP LOCKED / lease |
| alert-edge gateway | Deployment 或 StatefulSet | 每区域 2 个实例 | 需每实例独立 PVC 队列，Ingress 会话粘性非可靠性代替品 |
| alert-edge huatuo collector | Deployment 分片 / DaemonSet | 按节点及可达性 | 需要唯一订阅所有权 |
| Kafka | 3 Brokers | RF=3, min ISR=2 | 可复用现有 HA |
| PostgreSQL | 主 + 备 + PITR | 依现有资源决定 | 无脑堆副本并不等于自动 HA |

Edge 2 副本本身**不能保证本地 WAL 双副本**；若单盘故障的数据不可丢，应使用共享/复制日志、上游重试能力或区域消息存储。

## 3. 健康与自身告警

指标命名统一为 `alert_platform_<area>_<metric>`（P9-OBS-01）；`/metrics` 由各组件暴露。

- 接入：`alert_platform_ingest_events_total`、`alert_platform_ingest_rejected_total{reason}`、
  `alert_platform_ingest_batch_duration_seconds`。
- 消费：`alert_platform_processor_events_total{outcome}`、`alert_platform_processor_duration_seconds`、
  `alert_platform_consumer_lag{topic,group}`、`alert_platform_dlq_quarantined_total{topic}`。
- 投递：`alert_platform_notify_attempt_total{channel_type,result}`、`alert_platform_notify_pending`、
  `alert_platform_notify_lease_renew_failures_total{reason}`、`alert_platform_notify_authority_generation`、
  `alert_platform_notify_failed_total{reason}`（permanent/ssrf/max_attempts/channel_unavailable 死信）。
- Edge：`alert_platform_edge_wal_bytes`、`alert_platform_edge_wal_pending_records`、
  `alert_platform_edge_reconnect_total`、`alert_platform_edge_sse_gap_total`、
  `alert_platform_edge_wal_rejected_total`（WAL 写失败拒绝厂商批次）、
  `alert_platform_edge_upload_poison_total{status}`（中心 4xx 永久拒绝、留在 WAL 待人工重放）。
- 保留：`alert_platform_retention_receipts_deleted_total`、`alert_platform_retention_receipts_retained_total`。
- 归档（P9-CH-01）：`alert_platform_archive_written_total`、`alert_platform_archive_errors_total`、
  `alert_platform_archive_lag_seconds`、`alert_platform_archive_queue_pending`。
- 生命周期对账（P10-004）：`alert_platform_lifecycle_transitions_deleted_total`、
  `alert_platform_lifecycle_days_verified_total`、`alert_platform_lifecycle_days_unverified`。
- 业务（P9-OBS-06 待实现）：`alert_platform_alert_active_instances`、`alert_platform_incident_open`、
  `alert_platform_source_heartbeat_age_seconds{source}`。

高基数 ID（event/incident/pod/source uid/channel_id）只在日志/trace 中，**不作为 Prometheus Label**；
允许的 label：`reason`、`result`、`outcome`、`channel_type`、`topic`、`group`（来源心跳的 `source` 为
注册表内名称，数量受注册来源数约束）。

**自身告警与兜底（P9-OBS-07）**：Chart 提供可选 `prometheusRule.enabled`（默认关闭，需 Prometheus Operator
CRD），内置 IngestRejectRate / ConsumerLag / DLQGrowing / NotifyFailures / NotifyBacklog /
NotifyDeadLettered / NotifyRetryStorm / EdgeWALRejected / EdgeUploadPoison 九条规则，
`prometheusRule.labels` 适配各集群 rule selector，`extraRules` 追加自定义规则。
`ALERT_FALLBACK_WEBHOOK` 配置**独立兜底通道**：worker 关键任务 fail-stop 前直接 POST 该 webhook，
**不经过 notification_outbox**——通知链路本身故障时自身告警仍可送达；`ALERT_FALLBACK_ALLOW_PRIVATE`
仅本地/内网自建 webhook 时开启（默认拒绝私网，沿用 SSRF 拨号守卫）。

**产品内指标中心（P9-MC-01 / P10-006 租户隔离）**：`ALERT_PROMETHEUS_URL` 指向 Prometheus HTTP API 后，控制台"指标"页
通过 `GET /metrics/v1/catalog`（白名单目录）与 `GET /metrics/v1/query?metric=&start=&end=&step=`
查询趋势；客户端只能选择服务端目录中的指标，无法注入任意 PromQL；窗口 ≤24h、步长 ≥15s、点数 ≤2000。
未配置时接口 503、页面显示明确提示。

指标分两级，权限与查询边界不同：

| 级别 | 示例 | 可见性 | 查询行为 |
|---|---|---|---|
| `platform` | ingest/processor/notify/edge/archive 吞吐、consumer lag、DLQ | 仅 `metrics:platform`（仅 Platform Admin） | 全局聚合，无 tenant matcher |
| `tenant` | `active_instances`、`open_incidents`、`source_heartbeat_age` | 任意 `alerts:read` 角色 | 服务端强制注入 `{tenant="<调用者租户>"}`，前端无法绕过 |

业务 gauge（`alert_platform_alert_active_instances`、`alert_platform_incident_open`、
`alert_platform_source_heartbeat_age_seconds{tenant,source}`）由 telemetry sampler 按租户采样；
租户/来源删除后 Reset 清掉旧序列。**基数预算**：`tenant` label 受租户数上限约束（建议 ≤500），
`source` label 受注册来源数约束（建议 ≤2000/安装）；event/incident/pod/channel 等高基数 ID
永不进入 Prometheus label，只在日志/trace 中。

平台自身故障通知必须使用**独立兜底通道**，不能依赖正发生故障的同一套通知链路。

## 4. 发布顺序

1. Shadow 接入只观察、不通知，量化与上游现有告警的差异。
2. 单团队 + 非关键规则将通知权交给平台，避免双发。
3. 按来源/团队/环境扩大灰度，保留回退上游通知能力。
4. 运行 Chaos、DB failover、断网补传、SLO 压测。
5. 通过 Go/No-Go 评审后发布 v1.0。

## 5. SLO（方案目标，尚未实测）

- 入队后状态处理正常负载 P95 <= 3s。
- 无聚合等待的首次通知调度 P95 <= 10s。
- 100 EPS 稳态，2k EPS/10min 峰值。
- 审计和通知尝试日志 100% 可查询。
- Edge 中已确认持久化事件可断网恢复补传，但不承诺 SSE 源端无历史重放情况下的零丢失。

## 4. 传输与输入加固（AUD-007/016）

- **请求体上限**：Hertz 显式 `WithMaxRequestBodySize(8MiB)`（`platform.MaxRequestBodyBytes`），
  不再依赖框架隐式 4MiB；ingest 单事件序列化上限 `ingest.MaxEventBytes=256KiB`、单批
  `MaxBatchEvents=1000`，超限逐条/整批 **400** 并带明细（此前一律 500，Edge 会把毒批次当故障无限重试）。
  kafka-go `BatchBytes` 显式 1MiB，高于事件上限，single event 不可能触发 `MessageTooLargeError`。
- **ingest 限流**：认证后按 `tenant|source`（edge 凭证按 `tenant|edge:<id>`，未认证按 IP）令牌桶限流；
  `ALERT_INGEST_RATE_PER_SEC`（默认 500）/ `ALERT_INGEST_BURST`（默认 1000），超限 429 + `Retry-After`。
  凭证正缓存 30s（P9-R29），风暴下 PG 查询有界。
- **安全响应头**：所有响应带 `X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、
  `Referrer-Policy: no-referrer`、CSP（`frame-ancestors 'none'`、`object-src 'none'`，
  兼容内置控制台同源静态资源）与 `Permissions-Policy`。
- **readiness**：alert-api 默认探活 PostgreSQL + Kafka metadata（`ALERT_KAFKA_READINESS=true`）；
  无 Kafka 的 dev 集群必须显式设 `ALERT_KAFKA_READINESS=false`（启动会告警），生产不得关闭。
- **OTLP/TLS**：`OTLP_INSECURE` 可配（默认 true 以兼容本地 collector）；生产必须设 false，
  启动时会告警。`PGDSN` 含 `sslmode=disable` 时启动告警，生产应使用 `verify-full`。
- **Edge 拒绝计数**：`alert_platform_edge_wal_rejected_total`（WAL 写失败）与
  `alert_platform_edge_upload_poison_total{status}`（中心 4xx 永久拒绝）配套告警；
  毒批次保留在 WAL 供人工重放，不阻塞后续记录。

## 5. Worker Profile（P10-008）

同一镜像通过 `WORKER_PROFILE` 选择启动哪些后台循环，避免"扩 processor 副本 = 同时扩归档/清理/采样"：

| Profile | 启动任务 | 扩缩建议 |
|---|---|---|
| `all`（默认） | processor + relay/notifier/escalation + health/retention/telemetry/archive | 单副本或小规模 |
| `processor` | 仅 Kafka consumer group（processor） | 按消费 lag 横扩（5 副本 = 5 个 consumer，不再带来 5 套 singleton） |
| `notifier` | relay + notifier + escalation | 多副本安全：relay/notifier 持 DB lease，escalation 单飞 |
| `maintenance` | health-scheduler + retention + telemetry + archive | 建议单副本；全部持 `component_leases` 租约，误扩也只有一个执行者 |

未知 profile 直接启动失败（拼写错误不会静默回退到 `all`）。Helm：`worker.profile` → `WORKER_PROFILE`；
需要独立扩容 consumer 时启用 `workerProcessor.enabled=true`（同一镜像、固定 `WORKER_PROFILE=processor`、
独立 `replicas`），单例任务仍留在 `worker` Deployment 并由租约兜底。
Kafka processor 仍靠 consumer group 协调；retention/telemetry/archive/relay/escalation 的租约名分别为
`retention.cleanup` / `telemetry.sampler` / archive / `outbox.relay` / `escalation.correlate`。
