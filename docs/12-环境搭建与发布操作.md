## 本地一键启动（BASE-002 起）

```bash
make dev-up      # 构建并启动 alert-api(:8080)/alert-worker(:8081)/alert-edge(:8082)
                 # 自动验证三者 /healthz 200，并跑 trace_id 跨组件串联演示

```

- 配置基线在 `etc/config.yaml`；优先级 env（`ALERT_API_ADDR`/`ALERT_WORKER_ADDR`/`ALERT_EDGE_ADDR`/`LOG_LEVEL`/`OTLP_ENDPOINT`/`WORKER_PROFILE`）> YAML > default。

- 进程日志在 `.dev/logs/`，PID 在 `.dev/pids/`（均已 gitignore）。

## 镜像构建（BASE-004）

单镜像三入口（`Dockerfile`，多阶段 `$BUILDPLATFORM` 交叉编译，CGO 关闭，非 root 运行，基础镜像钉版 `golang:1.27.4-alpine` / `alpine:3.21`）：

```bash
docker build -t alert-platform:local --build-arg VERSION=0.1.0-dev+local .
# 运行（默认 entry = alert-api；按组件覆盖）
docker run -d --name api alert-platform:local
docker run -d --entrypoint /usr/local/bin/alert-worker alert-platform:local
# 健康探活：宿主端口转发不可用时从同网络命名空间旁路容器探
docker run --rm --network container:api alpine:3.21 wget -qO- http://127.0.0.1:8080/healthz
# 多架构 + SBOM（BuildKit 原生，SPDX-2.3 attestation 附于 OCI 输出）
docker buildx build --platform linux/amd64,linux/arm64 --sbom=true \
  --output type=oci,dest=image.tar .
```

- 配置：镜像内置 `etc/config.yaml` 基线（WORKDIR `/app`），env 覆盖优先；部署可用 ConfigMap 挂载替换。
- `version` 经 `-ldflags -X main.version=` 注入（CI 用 git short SHA）。
- CI（contract-ci.yml `image` job）：每次构建双平台+SBOM 并归档 OCI artifact；**merge main 推 dev registry 仅在 `DEV_REGISTRY` secret 配置后生效**（未配置时输出 blocker notice，job 其余部分照常验证）。

## 推荐流水线

1. PR 触发：Go format、vet、test、Buf lint/build/breaking、生成代码差异、Schema 测试、依赖扫描。
2. Merge：构建带 commit SHA 的不可变镜像；产出 SBOM、部署 Chart、变更清单。
3. Dev：迁移数据库 -> 灰度部署 -> 集成 E2E -> 观察队列/业务指标。
4. Preprod：压测与 Chaos、DB 备份恢复、边界安全检查。
5. Prod：Shadow -> 小范围交接通知权 -> 扩大灰度 -> Go/No-Go 评审。

## 回滚准则

- 优先回滚应用镜像和流量路由；数据库 Migration 需采用向前兼容 Expand/Migrate/Contract，不保证所有 DDL 可逆。
- 保留 Kafka Consumer/IDL 双向兼容窗口，避免老版本无法读新事件。
- 通知权交接必须可按规则回滚到上游，严禁同时两个系统不受控通知。
- 回滚前确认 PostgreSQL 中仍有待投递任务，避免遗漏或二次发送。

#### Edge 上传凭证（P0-03，2026-11-15 起）

内部上传 `POST /ingest/v1/events:batch` **不再匿名**：uploader 以来源注册表凭证
（`aps_...`，即 sources.json 同源的中央侧 token）作为 `Authorization: Bearer`
发送；服务端把批次内事件的 tenant_id/source_id/cluster_id **权威绑定**到凭证
（payload 自报不一致 → 403，缺席 → 以凭证回填）。

- 单源 Edge（现网全部形态）：`ALERT_EDGE_API_KEY` 直接配置该来源的明文
  `aps_` token（uploader 回退用它作为上传凭证 + 心跳 `X-Edge-Key`）。
- **多源 Edge（P8-P0-02 起，推荐）**：中央登记一个 Edge 上行身份——
  `edge_id → tenant_id → allowed_source_ids`，存入 `edge_uplink_credentials`
  （只存 token 的 SHA-256；`allowed_source_ids` 自动过滤已禁用来源）。Edge 侧：

  ```yaml
  edge_id: edge-01
  edge_uplink_token: aps_...   # 单一上行凭证，服务端按 allowed 集校验每个事件来源
  ```

  uploader 对全部来源统一发送该凭证并携带 `X-Edge-Id`；中央对批次内每个事件
  校验 `source_id ∈ allowed_source_ids` 且租户一致，越权/跨租户 → 403。
  登记（DBA 审核后执行，token 明文只出现一次）：

  ```sql
  INSERT INTO edge_uplink_credentials (edge_id, tenant_id, token_hash, allowed_source_ids)
  VALUES ('edge-01', '<tenant_uuid>',
          encode(sha256('aps_the_plaintext_token'::bytea), 'hex'),
          ARRAY['<source_uuid_df>','<source_uuid_am>']::uuid[]);
  ```

- **兼容的多源形态（过渡）**：`ALERT_EDGE_SOURCE_TOKENS`
  （JSON `{"<source_id>":"aps_..."}`）为每个来源配置各自 token。可行但把多个
  来源明文 token 复制到同一个 Edge，**不应作为长期方案**；新部署用上行身份。
- 心跳接口 `/edge/v1/heartbeat` 语义不变（仍校验 `X-Edge-Key`）。
- 轮换（上行身份）：先插入新 token 行，再 `UPDATE ... SET revoked_at=now()`
  吊销旧行——旧 token 立即 401，新 token 生效前不影响在途批次。
- 轮换（单源/兼容形态）：跟随 alert-platform-edge 的 180d 周期，与 sources.json 同步更新。

### DLQ 巡检与重放（R20/R21）

契约违例（缺 tenant/source/signal/severity、protobuf 解码失败）由 consumer 归类
Permanent：原消息写入 `alert.dlq.v1` 并提交 offset，**不会**打死 worker。DLQ 消息带
取证头：`dlq_error`（失败原因）、`original_topic` / `original_partition` / `original_offset`。

```bash
# 查看隔离消息（含头）
docker exec dev-kafka-1 kafka-console-consumer --bootstrap-server localhost:29092 \
  --topic alert.dlq.v1 --from-beginning --property print.headers=true --timeout-ms 3000

# 生产：确认 DLQ 深度
kafka-consumer-groups --bootstrap-server <broker> --describe --group <dlq-inspector>
```

处置原则：**不要直接删除**。修复上游数据/适配器后，按 `original_*` 头修复 payload 并
显式重放到原 topic（生产用受控重放脚本）；DLQ 持续增长视为来源契约回归信号，应联动
`alert_dlq_quarantine_total`（规划指标）告警。本地 compose 关闭自动建主题，脚本已
显式创建 `alert.dlq.v1` / `alert.lifecycle.v1`；新环境首装同理。

## 无集群内 registry 时的镜像交付（节点导入法，2026-11-14 rpi-k3s 实装验证）

集群节点可拉 docker.io 但没有可推送的 registry，且节点 containerd 拉取自定义镜像需改
`/etc/rancher/k3s/registries.yaml`（无节点 shell 时不可行）。**节点导入法**绕过拉取配置：

```bash
# 1) 本机构建目标架构镜像并导出（tag 用完整引用，导入后 kubelet 才能按名命中）
docker buildx build --platform linux/arm64 -t docker.io/library/alert-platform:<tag> --load .
docker save docker.io/library/alert-platform:<tag> -o /tmp/ap-image.tar

# 2) 特权 pod 挂宿主 containerd socket（钉在目标节点），tar 经 kubectl cp 进 pod
kubectl -n alert-platform apply -f - <<'YAML'   # hostPID + hostPath /run/k3s/containerd + emptyDir /scratch
...
YAML
POD_UID=$(kubectl -n alert-platform get pod image-import -o jsonpath='{.metadata.uid}')
kubectl -n alert-platform cp /tmp/ap-image.tar image-import:/scratch/ap-image.tar

# 3) 经宿主 mount ns 用宿主自带 ctr 导入 k8s.io 命名空间（路径经 kubelet emptyDir 反查）
kubectl -n alert-platform exec image-import -- nsenter -t 1 -m -- \
  ctr --address /run/k3s/containerd/containerd.sock -n k8s.io images import \
  "/var/lib/kubelet/pods/$POD_UID/volumes/kubernetes.io~empty-dir/scratch/ap-image.tar"
```

之后 `helm install --set image.pullPolicy=IfNotPresent --set nodeSelector.<节点>=<值>` 即可
（镜像必须含在 image 内：**migrations/ 目录与全部二进制**——本包曾漏 alert-migrate 与
migrations/ 导致 hook job 失败，教训已固化在 Dockerfile 注释）。
