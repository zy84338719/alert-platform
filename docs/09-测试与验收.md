# 09 · 分层测试、故障演练和发布门禁

> 逐任务的二值验收标准、验证方式与证据要求见 `docs/13-分阶段任务验收标准.md`；本文定义测试分层与阶段闸门。

## 1. 测试金字塔

- 单元测试：状态机、fingerprint、路由匹配、episode、策略版本、无数据状态。
- 契约测试：DeepFlow v7.2.3 **真实脱敏样本**、Alertmanager 批次、HUATUO CloudEvents/SSE；IDL 兼容性。
- 集成测试：Kafka/PG/Outbox/ClickHouse；重放、Offset、事务边界。
- E2E：来源 -> Edge -> Kafka -> Processor -> DB -> Notifier -> Mock Channel。
- 性能测试：100 EPS 稳态、2k EPS/10min、Edge 断网补传、PG 热点与 Kafka Lag。
- 混沌测试：Pod/节点、broker、PG 主库、网络分区、时钟漂移、重复/乱序、渠道 429/5xx。

### 2.1 用例明细（前置条件 / 执行步骤 / 判定值）

  通用前置：所有外部样本必须标注真实/合成（fixture 命名 `REAL-*` / `SYNTHETIC-*`）；所有判定同时检查结构化日志与指标计数，不只看返回码。

- **T-001 · DeepFlow v7.2.3 Critical 映射**
  - 前置：DeepFlow 源已在 Source Registry 登记并持有凭证；`contracts/external/deepflow/v7.2.3/` 下 Critical（`event_level=1`、`state=0`）fixture 就绪；Adapter 版本号已配置。
  - 步骤：① 向 DeepFlow 入口投递 fixture；② 取出产出的 CanonicalEvent；③ 逐字段比对 `mapping.yaml`。
  - 判定值：`severity=SEVERITY_CRITICAL`、`signal=EVENT_SIGNAL_FIRING`、`source_type=SOURCE_TYPE_DEEPFLOW`；`policy_id→external_rule_id`、`event_id→external_event_id`、`_target_uid→resource_uid`；未知字段保留在 `raw_payload`；`fingerprint` 由服务端重算（payload 自带指纹字段不采信）；入口返回 202 + `durable_batch_id`。
- **T-002 · DeepFlow Recovery 语义**
  - 前置：同 fixture 族中 Recovery 样本（`state=1` 或 `event_level=5`）；恢复关联键为 `event_id` 优先，其次 `policy_id+target_key+start_time`。
  - 步骤：① 投 Critical 建立活跃 episode；② 投同关联键 Recovery；③ 负例：投"同名但关联键不同"的恢复。
  - 判定值：② 后同一 `fingerprint`/`episode_key`，`monitor_state` firing→resolved，仅一条迁移记录；③ 不恢复任何告警，产生一条待对账/未匹配恢复的记录而非静默丢弃。
- **T-003 · Alertmanager 批量解析**
  - 前置：Alertmanager 源已登记；一次 POST 携带 ≥3 条 alert（含 1 对同 fingerprints 重复）。
  - 步骤：POST webhook → 逐 alert 比对。
  - 判定值：N 条 alert 产出 N 个 CanonicalEvent（绝不整批合并为一条）；每条独立 `event_key`；同指纹两条归并到同一 episode 并按重复观察处理；整体 202。
- **T-004 · HUATUO SSE 中断重连**
  - 前置：可编程 SSE Mock（支持 Last-Event-ID 与心跳）；订阅者在线并已收到事件。
  - 步骤：① 订阅并收事件；② 断连超过心跳阈值；③ 重连；④ 检查断连窗口内事件。
  - 判定值：重连后订阅恢复；断连期间的未确认缺口产生显式 gap/对账记录；断连不生成任何 Resolved/Stale 副作用；Edge 缓冲水位与最老未确认年龄指标可查。
- **T-005 · 千次重复 Firing**
  - 前置：单测级（状态机+存储桩）与集成级（Kafka+PG）各执行一遍；同一 `event_key`。
  - 步骤：并发+顺序混合投递同一 Firing 1000 次。
  - 判定值：`alert_transitions` 该 episode 恰 1 条 firing 迁移；`last_observed_at` 单调前进；同策略通知任务恰 1 条；其余 999 次命中重复观察路径（`repeat-firing`/`duplicate-older-observation`），`version` 不因重复观察增长。
- **T-006 · 旧 Firing 不重开 episode**
  - 前置：episode 已 resolved；备一条 `occurred_at` 早于恢复的 Firing。
  - 步骤：投递旧 Firing → 查实例与迁移表 → 再投一条恢复后新开始的 Firing。
  - 判定值：旧 Firing 被拒绝重开（`ErrEpisodeClosed` 语义），事件本体仍入 `event_receipts`，拒绝计数指标 +1；新开始 Firing 创建**新** episode_key。
- **T-007 · Commit 成功 Offset 失败重放**
  - 前置：Kafka+PG 集成环境；outbox 与业务表同库；消费组运行中。
  - 步骤：① 消费事件并 PG commit；② 在 offset commit 前注入进程故障；③ 重启触发重放。
  - 判定值：重放后通知任务零重复（outbox 幂等键约束生效）；`uq_alert_transition_event` 保证迁移零重复；offset 最终前进；无消息进入死信。
- **T-008 · 通知渠道故障**
  - 前置：Mock 渠道可编程返回 500 / 429（带 Retry-After）/ 挂起超时；通知任务已入队。
  - 步骤：分别注入三类故障并观察重试序列直至终态。
  - 判定值：退避序列符合策略且尊重 Retry-After；超限后进入终态 failed；每次尝试均有审计记录（含渠道返回摘要）；任务持有 lease 期间不被并发重复发送；失败/成功计数指标正确。
- **T-009 · 静默窗口抑制**
  - 前置：创建覆盖目标告警的静默规则（matchers + 有效期）。
  - 步骤：静默窗口内投 Firing；窗口过期后投同指纹新事件。
  - 判定值：窗口内事件与状态机正常入库、通知被抑制且抑制命中记录可查（含命中规则 ID/版本）；监控状态未被静默修改；过期后通知恢复发送。
- **T-010 · PG 主库故障**
  - 前置：PG 故障注入点（主备切换或 kill）；消费者运行中。
  - 步骤：注入故障 → 观察消费与 offset 行为 → 恢复。
  - 判定值：事务失败期间绝不提交 offset；消费者退避重试而非崩溃或跳过；恢复后自最后 committed offset 续消费；无跨表撕裂提交（业务表与 outbox 要么都在要么都不在）。
- **T-011 · Edge 断连 30 分钟**
  - 前置：Edge 本地 WAL（fsync）+ 中心可达；持续事件流。
  - 步骤：断网 30 分钟（期间持续接收并本地 ACK）→ 恢复 → 可选重启 Edge 进程。
  - 判定值：断连期间 ACK 过的事件在重启后仍完整存在于 WAL；恢复后自动补传且 `transport_id` 复用；中心去重后业务效果无重复；WAL compact 后磁盘占用受控；缓冲水位指标全程可见。
- **T-012 · 租户伪造**
  - 前置：source A 凭证（tenant A）；构造 payload/头部声称 tenant B 的请求。
  - 步骤：以 A 凭证投递声称 B 的事件；再尝试用 B 租户查询接口读取。
  - 判定值：服务端拒绝（403）或强制以服务端推导租户改写；任何路径下 payload 自带租户不得入库；拒绝行为入审计；A 的数据对 B 查询不可见。
- **T-013 · 出站 SSRF**
  - 前置：通知渠道/Webhook 目标地址可配置；出站必须经统一 egress。
  - 步骤：分别配置指向 `169.254.169.254`、`127.0.0.1`、内网 CIDR、IPv6 等价地址与 DNS 重绑定域名的 URL。
  - 判定值：配置校验与运行时解析双重拦截；每次拦截入审计；合法公网目标不受影响。
- **T-014 · 性能双档**
  - 前置：压测环境规格（机器/PG/Kafka 参数）与消息大小分布已书面记录；指标看板就绪。
  - 步骤：100 EPS 稳态 ≥1h → 2k EPS 冲击 10min → 观察回敛。
  - 判定值：稳态下入队后状态处理 P95≤3s、首次通知调度 P95≤10s、无不透明丢弃（每事件终态可解释）；峰值无丢失（或显式背压/拒绝有计数）、Kafka lag 有界且峰后回敛、PG 无连接堆积；P50/95/99 全量归档。
- **T-015 · IP 复用不误关联**
  - 前置：同一 IP 在 t1 映射 Pod A、t2 映射 Pod B（entity_uid 不同）。
  - 步骤：构造两轮事件分别携带不同 `entity_uid` 投递。
  - 判定值：产生两个独立 fingerprint/episode；IP 相同不触发归并；Pod A 的 episode 不被 Pod B 事件恢复或改写。
- **T-016 · 同名不同源不误合并**
  - 前置：source 1、source 2 均配置同名 `alert_name`。
  - 步骤：两源各投一条 Firing，随后仅对 source 1 投 Recovery。
  - 判定值：两条告警 fingerprint 不同（source 实例参与身份）、episode 相互独立；source 1 恢复不影响 source 2 的 firing 状态。

## 3. 每阶段 Go / No-Go

- W1：真实来源样本、领域状态语义和 ACK 契约评审通过。
- W3：IDL build/lint/generate，标准库 Go 示例测试，Kafka/PG 集成链路可跑。
- W6：幂等/乱序/episode 测试，恢复状态对账测试通过。
- W9：至少两种真实通知渠道、用户 ACK、静默及审计闭环；**多租户认证/RBAC/对象级授权与审计通过（T-012/T-013，FR-009）**；MVP 灰度可用。
- W12：HUATUO 事件和多集群 Edge 补传，无法回放的缺口被检测和记录。
- W17：Incident 关联可解释、人工拆分可回退、历史查询可用。
- W20：压测、混沌、恢复演练、安全审核、灰度/回滚均通过，无 P0/P1 阻断缺陷。

## 4. 必须保存的测试产物

- Fixture 来源/版本/脱敏方式、生成时间。
- Load Test 环境规格、消息大小分布、EPS、P50/95/99、错误率、Kafka Lag、PG IO。
- Chaos 故障注入时间线、回滚步骤、事件丢失/重复影响统计。
- Release Candidate 变更清单与 Schema breaking 结果。
